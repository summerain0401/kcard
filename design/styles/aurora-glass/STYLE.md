# aurora-glass 风格宪法

> 设计部交付物。本文件定义**什么不可违反**;可自由搭配的参数及其取值域见同目录 `space.json`。
> 2026-07-27 新建,kcard 的第三套风格。

## 一、这套风格是什么

暗色玻璃面板浮在几团硬边大色斑之上。色斑被画布边缘裁成弧形,
透过面板只剩极淡的色晕;面板本身近乎不透明的深炭色,靠**大半径背景模糊**
与一道顶边高光获得厚度。字体全部无衬线,字号小、字距大、留白多。

视觉张力来自**「浮起来」的物理关系**——色斑在下、玻璃在上、主体在玻璃上,
三层各自清晰,不来自透明度或发光。与另两套风格构成三角:
`editorial-mono` 是暗夜画册(竖排宋体、无圆角),`almanac` 是纸本图鉴
(横排衬线、无圆角),本风格是**当代产品视觉**(无衬线、大圆角、材质分层)。

## 二、构成要素(缺一即不成立)

| # | 要素 | 现行实现 |
|---|---|---|
| E1 | **硬边大色斑** | 2–4 个正圆,尺寸接近画布量级,必须被画布边缘裁切 |
| E2 | **无彩色斑** | 色斑中至少一颗接近无彩(近白或近灰),作为画面的呼吸口 |
| E3 | **深色玻璃面板** | 内缩于画布,承载全部文字,`backdrop-filter` 大半径模糊 |
| E4 | **顶边高光** | 面板左上角一道渐隐白,玻璃厚度感的唯一来源 |
| E5 | **章节导航片** | 一列/一排小玻璃方片,内含章节编号,首片以 accent 描边。片数 = **实际渲染的**章节数,不是内容池的总块数 |
| E6 | **玻璃小元件** | 标签胶囊、指标槽、引文块自身即小块玻璃,与大面板同材质不同厚度 |
| E7 | **字母印记兜底** | 无主图时用 `nameEn` 首字母的巨型描边字,而非 emoji |
| E8 | **无衬线全域** | 标题、正文、编号一律无衬线,与另两套风格结构性区分 |
| E9 | **手机可读的字号与容量** | 正文 ≥ 26px(1080 画布),且渲染块数受限以压住长宽比,二者缺一不可,见第四节 |
| E10 | **章节区的结构由骨架决定** | 引擎为每块输出 `data-i` / `data-style` 钩子、为容器输出 `data-n`,骨架据此排布。六个骨架的章节区结构必须彼此可辨,不能只靠头版和配色区分 |

## 三、禁则(硬约束,机器可校验)

| # | 禁则 | 判据 | 理由 |
|---|---|---|---|
| H1 | 玻璃面板必须是深色 | `glass.lightness ≤ 0.26` | 浅色半透明面板即「小红书毛玻璃」,本项目已两次否定该方向 |
| H2 | 玻璃不得过透 | `glass.opacity ≥ 0.55` | 透太多则文字骑在色斑上,画面花、可读性塌 |
| H3 | 必须有真实背景模糊 | `glass.blur ≥ 20` | 没有 `backdrop-filter` 的深色板不是玻璃,只是深色板 |
| H4 | 面板必须浮于幕布之上 | `glass.lightness > scrim.lightness` | 面板比底幕暗就成了凹槽,三层关系反转 |
| H5 | 禁发光与彩色投影 | 不得出现彩色 `box-shadow` / `drop-shadow`;不得出现任何 `text-shadow` | 发光是「科技风模板」的标志,本项目明确排除 |
| H6 | 圆角必须足够大且统一 | `glass.radius ≥ 16`,面板与小元件共用同一套半径参数 | 小圆角在大面板上像未完成的方框;本风格是三套里唯一鼓励圆角的 |
| H7 | 必须无衬线 | 标题与正文字体栈均为 sans 族 | 衬线是另两套风格的地盘(E8) |
| H8 | 禁 emoji | 渲染产物中不含 emoji 码点,缺图走字母印记(E7) | emoji 是廉价感的主要来源 |
| H9 | 正文对比度达标 | `contrast(ink, glass) ≥ 4.5:1` | 可读性底线 |

## 四、高级感判据(软约束,人评)

机器拦不住"合法但难看"。以下由设计部在**生产组上线时**一次性把关:

- **裁切**——色斑必须有相当比例落在画布外,完整的圆会读成图标而非光源
- **克制**——accent 只出现在章节编号、指标填充、导航首片描边、页脚圆点,不作区块填充
- **留白**——面板内边距与头版留白要足;这套风格靠空,不靠满
- **层次**——色斑 / 面板 / 主体三层的明度必须拉开;糊成一片时先压幕布,不要加发光
- **字距**——小号无衬线要给足字距,大标题要负字距;两者反过来立刻显廉价

### 容量判据(E9 的落地规则)

初版把正文定成 16px,是照桌面网页的习惯定的,**错了**。成品是 1080px 宽的图,
在手机上会被缩到约 36%,16px 到手机上只剩 6pt,不足该有字号的三分之一。

但把字号提上去还不够,甚至可能更糟:**长图会被整体缩小**。手机常按"整图适配"
显示(聊天缩略图、九宫格、查看器默认),此时决定可读性的不是绝对字号,而是
**正文字号 ÷ 卡片高度**。实测(28px 正文,390×844pt 屏):

| 长宽比 | 整图适配时的正文视觉 |
|---|---|
| 1:1.5 | 15.6pt — 任何显示方式都清楚 |
| 1:1.8 | 12.1pt — 可辨 |
| 1:2.0 | 10.9pt — 勉强 |
| 1:2.55 | 8.6pt — 比 16px 正文的短卡还差 |

所以判据是**字号与容量一起看**:

- 正文 **≥ 26px**(宪法 E9,`type.bodySize` 的取值域下限已按此设定)
- 内容量由 `layout.blockLimit` 控制,**不靠删内容**——见下面的内容池模型
- 选题信息量确实超了就**拆成多张卡**,不要靠缩小字号塞进一张

### 内容池模型(2026-07-28 起)

`card.json` 的 `blocks[]` 是**内容池**,不是渲染清单:内容写满(上限 6 块),
每个骨架按自己的密度用 `layout.blockLimit` 取前 N 块。顺序即优先级,
最重要的写在前面。

这条改动的由来:上一轮修字号时,卡片变长,我是**删掉 card.json 里的条目**
去压长宽比的——内容被永久破坏,换个排版也回不来。池子模型把「写多少」和
「露出多少」拆开,同一份内容在紧凑骨架上取 4 块、在密度高的骨架上取 6 块,
两边都成立,谁也不用删。

**容量是每个骨架自己的属性,不是全风格一个数。** 六版实测(1080 画布,
390×844pt 屏,"缩略图"指整图适配显示时的正文视觉字号):

| 搭配 | 骨架 | 取块 | 长宽比 | 缩略图 | px/块 |
|---|---|---|---|---|---|
| `amber` | `e-mosaic` | 4 | 1:1.67 | 12.2pt | 452 |
| `onyx` | `c-bleed-poster` | 5 | 1:1.81 | 11.2pt | 391 |
| `ember` | `a-panel-split` | 4 | 1:1.88 | 11.7pt | 507 |
| `verdant` | `d-timeline` | 5 | 1:2.15 | 9.8pt | 464 |
| `mist` | `b-panel-center` | 5 | 1:2.19 | 10.0pt | 472 |
| `quartz` | `f-index` | 6 | 1:2.33 | 8.7pt | 420 |

每块占用高度在 391–507px 之间浮动,差出近三成——所以「几块合适」必须
逐骨架实测,不能照抄别的骨架。加新骨架时同样要量一遍再定它的 `blockLimit`。

`quartz` 是六版里唯一取满 6 块的,长宽比 1:2.33、缩略图 8.7pt 已是可用区间的
下沿。它成立的前提是 `f-index` 本就是给「无主图、纯文字、预期滑动阅读」的
选题用的;其余骨架不要照此放宽。

这条判据不做机器闸门(需要实际渲染量高度,而 `style-check.py` 不跑
Playwright),由设计部在生产组上线时看一眼 `output.png` 的长宽比把关。

## 五、边界

### 5.1 骨架 vs 引擎(2026-07-28 修订)

原先的分工是「骨架只负责头版五元素的定位」。那条线把章节区整个锁在引擎里,
结果是**换骨架只能换头版构图,章节区必然雷同**——三套风格的 section DOM 曾经
逐字节相同,骨架 CSS 连单个 section 都选不中。本风格自 2026-07-28 起改为:

| | 骨架(`layouts/*.css`) | 引擎(`engine.html`) |
|---|---|---|
| 管 | 头版元素定位、色斑落点、**章节区排布**:网格模板、跨列、顺序、逐块差异化 | 排版层级、配色、材质、块正文的内部构造 |

一句话:**骨架管「块怎么摆」,引擎管「块长什么样」**。

引擎为此输出三个钩子(E10),骨架用不用都行,不加 CSS 时渲染结果完全不变:

| 钩子 | 位置 | 用途 |
|---|---|---|
| `data-n` | `.grid` | 实际渲染的块数,骨架据此切换网格 |
| `data-i` | `.section` | 索引(0 起),骨架据此做逐块差异化 |
| `data-style` | `.section` | block 类型,骨架据此按类型排布 |

优先用 `data-i` 而非 `:nth-child`:前者指向**内容顺序**,后者指向 DOM 位置,
骨架一旦用 `order` 重排两者就会分叉。

内容层写死的 `span: "full"` 与骨架的跨列规则同特异度,而骨架 CSS 在引擎样式
**之后**注入,故骨架总能覆写它。各骨架应显式表态如何处置 `span-full`,
不要放任内容层的版式决策漏进来。

### 5.2 宪法 vs 参数空间

| 生产组可自由调 | 生产组不可越界 |
|---|---|
| 幕布/面板/文字的色相饱和明度(在 H1、H4 域内) | 不得把面板调浅、调透、调平(H1–H3) |
| 色斑数量、色相偏移、饱和明度、尺寸、模糊 | 不得让色斑全部有彩(E2) |
| 圆角、边框、顶边高光、投影强度 | 不得引入彩色投影或任何发光(H5) |
| 字号级差、字距、字重、无衬线字体栈 | 不得改用衬线(H7) |
| 栏数、栏距、取块数、面板内缩与内边距、主体尺寸、导航片尺寸 | 不得取消面板改为通版排字 |
| 换骨架(六个任选)、覆写 `palette.accent` 恢复每卡取色 | 不得让六个骨架的章节区结构退化成同一种(E10) |

各维度取值域见 `space.json`。参数空间不够用 → 向设计部提案扩展维度;
需要改变上表右列 → 那是**另一套风格**,不是本风格的调教。

## 六、数据契约

复用 kcard 的通用卡片结构(`emoji` / `name` / `nameEn` / `category` /
`themeColor` / `hero` / `blocks[]`),因此**任何已有生产组的 card.json
不加字段即可切换到本风格渲染**。

本风格不新增任何字段。`emoji` 字段被**刻意忽略**(宪法 H8):无 `hero` 时
不退回 emoji,而是用 `nameEn` 首字母渲染字母印记(E7)。因此 `nameEn`
在本风格下比在另两套里更重要——缺失时印记退化为 `name` 首字。

字段详解见同目录 `schema.md`。

## 七、已知偏离

- **字体依赖 macOS 系统字体**(PingFang SC / Avenir Next)。这是**有意接受的约束,
  不是待办**——本项目按 macOS 单机渲染设计,不追求跨平台一致。
- **`backdrop-filter` 依赖 Chromium**。渲染链路固定为 Playwright + Chromium,
  该属性在此环境稳定;若将来换渲染器需重新验证 E3/E4 的实际效果。
- **色斑位置属骨架职责**。引擎只算色斑的颜色与尺寸,`top/left` 全部由
  `layouts/*.css` 给出——构图是版式决策,引擎不替骨架决定。
